## Authentication Bypass via JWT algorithm manipulation

Checking the session cookies after login, I find **two JWT cookies**: `session` and `token`. Only the `token` cookie could be decoded. Inspecting its contents:

![JWT token decoded — contains role claim](/writeups/intigriti/1125/img3.png)

The token contains a `role` claim. The obvious approach is to change the role to `admin`, but the **JWT signature** blocks any modification — the server rejects tokens with an invalid signature.

**Bypass technique:** setting the algorithm field to `"none"`. With `alg: none`, the JWT specification requires no signature — the server accepts the token without verifying it. Modifying the payload to set `"role": "admin"` and stripping the signature:

![JWT algorithm none bypass — modified token accepted](/writeups/intigriti/1125/img4.png)

The modified JWT is accepted as valid and I gain access to the admin panel:

![Admin panel access granted](/writeups/intigriti/1125/img5.png)

## SSTI → RCE

Inside the admin panel, the profile page allows updating a **display name** that is reflected back in the UI. Two interesting attack vectors: XSS or SSTI. Since the challenge requires RCE without any user interaction, I focused exclusively on SSTI.

Testing the name field with SSTI detection payloads to fingerprint the template engine:

![SSTI payload testing in the name field](/writeups/intigriti/1125/img6.png)
